What counts as a successful walkthrough?

You should be able to inspect a real captured conversation, see guidelines generated from that conversation, choose which guidelines to serve, and prove that Cortex injected those serving IDs into the second task attempt. Separately, the grader tells you whether the agent actually completed the task.

Task you compare

Orchid Analytics, June 2026 production revenue: ledger_b. The before and after runs have identical task data and prompts, separate directories, and fresh session IDs.

Task you learn from

Northwind Studio, April 2026 production revenue: ledger_train. Only this training conversation goes into guideline generation.

You issue each command manually. The repository’s workflow runner handles fresh fixtures, service processes, session IDs, and independent grading. You inspect the configuration and artifacts at every boundary.

The latest recorded six-case run passed 4/6 with Evolve versus 2/6 without. Orchid changed from an incorrect report in 33 turns to an exact report in 16. Your fresh model responses, guideline IDs, and pass/fail outcomes can differ. A baseline pass or an empty guideline set is a valid observation.

Plan for three agent invocations plus a short LLM connection check, reflection, and retrieval. Each agent invocation has a 240-second timeout and a $1 CLI budget cap; the connection check, learning, and retrieval calls are additional. No Docker, Milvus, Langfuse, or everyday Cortex service installation is needed for this filesystem-backed demo.

Prepare the Cortex CA and configure the LLM gateway

Cortex requires a signing certificate, private key, and trust certificate named tls.crt, tls.key, and ca.crt. If you chose an existing Cortex CA, check that all three exist and skip the generation block.

For a new demo CA directory only:

mkdir -p "$DEMO_CA_DIR"
chmod 700 "$DEMO_CA_DIR"
if [ -e "$DEMO_CA_DIR/tls.key" ] || [ -e "$DEMO_CA_DIR/tls.crt" ]; then
  printf 'A CA already exists here; reuse it or choose a new DEMO_CA_DIR.\n'
else
  cat > "$DEMO_CA_DIR/ca.cnf" <<'CA_CONFIG'
[req]
prompt = no
distinguished_name = dn
x509_extensions = v3_ca
[dn]
CN = Cortex Evolve Manual Demo CA
[v3_ca]
basicConstraints = critical,CA:TRUE
keyUsage = critical,keyCertSign,cRLSign
CA_CONFIG
  openssl req -x509 -newkey rsa:2048 -nodes -sha256 -days 30 \
    -config "$DEMO_CA_DIR/ca.cnf" \
    -keyout "$DEMO_CA_DIR/tls.key" -out "$DEMO_CA_DIR/tls.crt"
  cp "$DEMO_CA_DIR/tls.crt" "$DEMO_CA_DIR/ca.crt"
  chmod 600 "$DEMO_CA_DIR/tls.key"
fi
test -f "$DEMO_CA_DIR/tls.key"
test -f "$DEMO_CA_DIR/tls.crt"
openssl x509 -in "$DEMO_CA_DIR/ca.crt" -noout -subject
You should seeOpenSSL may print key-generation progress, then the certificate subject. A newly generated CA has subject Cortex Evolve Manual Demo CA. An existing CA has its own subject. The runner configures the agent’s NODE_EXTRA_CA_CERTS for this CA; installing it into the OS trust store is unnecessary for this demo.

Configure the gateway used by Evolve and the task agent

Evolve needs an LLM to generate, reconcile, and retrieve guidelines. In this demo, it calls your gateway’s OpenAI-compatible API; Claude Code calls the same gateway’s Anthropic-compatible API. Cortex’s proxy/MCP addresses are separate from this LLM endpoint.

Paste the block below, then enter your gateway URL and key when prompted. The block normalizes a trailing /v1, hides key entry, and writes both clients’ configuration into the private gateway.env file.

{
printf 'Gateway root URL: '
IFS= read -r DEMO_GATEWAY_URL
printf 'Gateway API key (hidden): '
IFS= read -r -s DEMO_GATEWAY_KEY
printf '\n'

if [ -z "$DEMO_GATEWAY_URL" ] || [ -z "$DEMO_GATEWAY_KEY" ]; then
  printf 'Both values are required. Paste this block again to retry.\n'
else
  DEMO_GATEWAY_URL="${DEMO_GATEWAY_URL%/}"
  DEMO_GATEWAY_URL="${DEMO_GATEWAY_URL%/v1}"
  (
    umask 077
    printf 'ANTHROPIC_BASE_URL=%s\nANTHROPIC_API_KEY=%s\nOPENAI_BASE_URL=%s/v1\nOPENAI_API_KEY=%s\nEVOLVE_CUSTOM_LLM_PROVIDER=openai\n' \
      "$DEMO_GATEWAY_URL" "$DEMO_GATEWAY_KEY" \
      "$DEMO_GATEWAY_URL" "$DEMO_GATEWAY_KEY" > "$DEMO_CREDENTIALS"
  )
  chmod 600 "$DEMO_CREDENTIALS"
  printf 'Gateway configuration saved to %s\n' "$DEMO_CREDENTIALS"
fi
unset DEMO_GATEWAY_KEY DEMO_GATEWAY_URL
test -s "$DEMO_CREDENTIALS"
}
You should seeTwo prompts followed by Gateway configuration saved to …/gateway.env. The file check succeeds silently; the key is never printed. The same key is used for the gateway’s Anthropic requests and Evolve’s OpenAI-compatible requests. An existing file using ANTHROPIC_AUTH_TOKEN is also accepted by the runner.

Test Evolve’s actual LLM settings before starting services

A readable model catalog does not prove inference works. The following uses Evolve’s LLMSettings and the same LiteLLM completion function used for learning. It prints only the endpoint, provider, model, and whether a key is present, then makes one small model call.

uv run --no-sync python - <<'LLM_CHECK_PY'
import json
import os
from pathlib import Path
from experiments.cortex_learning_demo import run as driver

driver.CREDENTIALS = Path(os.environ["DEMO_CREDENTIALS"])
driver.ARTIFACTS = Path(os.environ["DEMO_RESULTS"])
state = json.loads((driver.ARTIFACTS / "state.json").read_text())
environment = driver.base_env(state["model"])
os.environ.update(environment)

from altk_evolve.config.llm import LLMSettings
from litellm import completion

settings = LLMSettings()
print(json.dumps({
    "provider": settings.custom_llm_provider,
    "guidelines_model": settings.guidelines_model,
    "base_url": environment["OPENAI_BASE_URL"],
    "api_key_configured": bool(environment["OPENAI_API_KEY"]),
}, indent=2))
response = completion(
    model=settings.guidelines_model,
    custom_llm_provider=settings.custom_llm_provider,
    messages=[{"role": "user", "content": "Reply with exactly EVOLVE_LLM_OK."}],
    max_tokens=32,
    temperature=0,
    timeout=45,
)
reply = response.choices[0].message.content
if not reply:
    raise SystemExit("The LLM returned an empty reply; inspect the gateway response.")
print(json.dumps({"llm_connection": "ok", "reply": reply}, indent=2))
LLM_CHECK_PY
You should seeprovider: openai, your selected guideline model, your gateway’s /v1 URL, api_key_configured: true, and a reply such as {"llm_connection": "ok", "reply": "EVOLVE_LLM_OK"}. This confirms Evolve can make an inference request through the configured protocol; the learning step will exercise its longer prompts.

If the call fails, check the OpenAI-compatible inference route, key permissions, exact model ID, and gateway logs before continuing. Model-not-found or authorization errors require fixing the gateway configuration, even when the catalog request succeeded. If you open a new terminal, restore the paths/helper and repeat the model exports before starting or learning.
