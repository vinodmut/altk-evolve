02 / The pieces and their connections

Cortex records and injects. Evolve learns and retrieves.

Model traffic passes through Cortex. Tool execution stays in the agent’s local trial directory. For training, the experiment explicitly ingests a recorded Cortex session into Evolve, adds the independent outcome, and generates candidate guidelines. Reviewed guidelines are then served through MCP to later model requests.

Model traffic & guideline retrievalTraining-only learning pathLocal execution & grading

Both loops are shown. Training uses Northwind Studio only; evaluation reads the frozen guideline set.

Why the bridge matters

The gateway ignored later text blocks in Anthropic’s system array, including Cortex’s appended Evolve block. The bridge preserves every block in one string. A separate model readback confirmed that the injected instruction was visible. Both arms use the bridge.

Sources: diagnostic, bridge implementation, model-visible readback.

What is isolated in this experiment

The agent starts with a fresh session and working directory, native memory disabled, and no agent-side MCP servers. Cortex calls Evolve MCP. Learning is manually selected from training; Cortex’s automatic idle learning stays disabled during evaluation.

The billing “service” is a local CLI backed by synthetic JSON files, rather than a remote billing system.

03 / The task, in detail

Reconcile May revenue for Maple Workshop.

This is the first held-out case in the predeclared plan: production account account-202, reporting month 2026-05. The agent receives this exact prompt in both arms.

Reconcile 2026-05 revenue for Maple Workshop's production account according to the billing service's accounting contract. Use the local service via `python3 ops.py`; its --help describes the API. Save report.json with totals_minor (currency to integer minor-unit net revenue) and included_event_ids (sorted distinct IDs). Return the same JSON in your final answer.

The same company name also resolves to a sandbox account. The export contains all 15 raw rows, even when a customer ID is supplied; the contract requires the agent to apply account filtering itself.

1

Collapse revisions first

For each event ID, keep its greatest numeric revision across the entire export. Equal-revision replays are identical. Do this before every downstream filter.

2

Production account only

Resolve the customer with find-customer. Keep only account-202; discard the sandbox rows.

3

Settled events only

Pending and voided events contribute nothing. A revision that voids a prior event must win before status filtering.

4

UTC month boundaries

Include timestamps from May 1 at 00:00Z up to, and excluding, June 1 at 00:00Z. Parse offsets; the date substring is insufficient.

5

Subtract positive refunds

Both captures and refunds carry positive magnitudes in minor units. Add captures, subtract refunds, and keep currencies separate.

6

Save and return the report

Write valid report.json with integer totals_minor and sorted distinct included_event_ids. Return the same JSON.

04 / From a training failure to reusable advice

The guidelines came from Northwind Studio.

Training used April 2026 data for a different customer. The first attempt returned correct totals and event IDs, but did not save the required file. Evolve processed that failed trajectory in standard mode. After independent feedback, the agent saved and verified the report; fast-consistency processing then analyzed the session including its recovery.

STEP 1 · INITIAL ATTEMPT

Correct answer, missing artifact

The answer was USD 12,176 and EUR 4,224, with the right event IDs. The saved_report check failed. Standard extraction generated candidate 1: compute and create the required output in code.

STEP 2 · FEEDBACK & RECOVERY

Save, read back, then learn

The same session received the failed-check feedback. The agent wrote the file and all checks passed. Fast-consistency processing generated candidates 2, 3, and 4: command help, broader search, and contract sequencing.

STEP 3 · REVIEW & FREEZE

Three guidelines served unchanged

Candidates 1, 2, 4 were selected before evaluation and copied unchanged to the reviewed namespace as served IDs 1, 2, 3. The six cases and alternating arm order were frozen. Evaluation trajectories were never used for learning.

Training session: 62598afa-9f2b-41c1-9be4-2f0c82bbc51d. Standard input: 17 paired tool calls/results. Session after recovery: 20 pairs. The recovery analysis includes the earlier attempt; it is not an independent new training task.

The exact generated and injected guidelines

These are the recorded model-generated statements. The “observed use” annotations describe the Maple trajectory; they are not additional injected instructions.

Candidate 1 → served ID 1 · standard
Explicitly perform the required data reconciliation and report creation in code when no single-tool command exists to generate the final output in the expected format.

When it applies. When the available tooling lacks an integrated command to directly produce the required report or output artifact.

Generated rationale. When a CLI does not provide an all-in-one reconciliation/report command, the agent must synthesize the process using individual outputs to fulfill task requirements, including generating and saving the required report file.

Generated implementation steps
  1. Extract the relevant data from all necessary source files (e.g., ledger, contract).
  2. Apply the reconciliation rules step by step in code (such as Python), following all contract instructions.
  3. Assemble the output into the required structure (e.g., report.json with all required keys and values).
  4. Save the output to the specified file, ensuring it matches both content and naming requirements.

Observed use: Maple: the agent executed Python and saved report.json.

Candidate 2 → served ID 2 · consistency-fast
Always reference command-specific --help output to determine required argument patterns and avoid misusing positional or named arguments.

When it applies. When interacting with a command-line tool or API, especially after encountering argument or usage errors.

Generated rationale. The agent initially guessed argument forms (e.g., '--name', '--environment') for commands, leading to repeated errors before consulting --help for the correct usage. Reviewing --help immediately can prevent wasted steps and errors.

Generated implementation steps
  1. Upon encountering an error regarding command usage or invalid arguments, immediately invoke the tool's --help or the specific subcommand's --help.
  2. Use the presented argument and usage structure as the basis for constructing further commands.

Observed use: Maple: the agent consulted help for revenue-contract, find-customer, and ledger-export.

Candidate 4 → served ID 3 · consistency-fast
Apply instructions from domain contracts or specifications in strict sequential order, resolving each clause before proceeding to downstream filters or computations.

When it applies. When implementing a business or data processing workflow governed by an explicit procedural contract or specification.

Generated rationale. The agent followed the detailed contract protocol, especially collapsing events by revision before filtering by date and status, corresponding to the mandated order of operations and ensuring both corrections and voids are handled correctly.

Generated implementation steps
  1. Carefully read and extract each procedural step from the contract or ruleset.
  2. Implement each filter or transformation step only after all mandated previous steps are resolved — for example, collapse by event revision before status/date filtering.

Observed use: Maple: the code selected maximum revisions before applying account, status, and UTC date filters.

The fourth generated candidate was not selected
When a filtering or search command returns insufficient results, broaden the query by using partial or fuzzy terms to discover possible candidates.

Candidate 3 was generated in consistency mode. It was omitted before the held-out evaluation. This is why candidate ID 4 becomes served ID 3.

python3 -c '
import json
from datetime import datetime, timezone

with open("ledger2026-05.json") as f:
    ledger = json.load(f)

# Step 1: Find the greatest revision per event_id across the entire export
max_revision = {}
for row in ledger:
    eid = row["event_id"]
    rev = row["revision"]
    if eid not in max_revision or rev > max_revision[eid]:
        max_revision[eid] = rev

# Step 2: Collapse rows by event_id using only the greatest revision. Ignore lower revisions.
collapsed = {}
for row in ledger:
    eid = row["event_id"]
    if row["revision"] == max_revision[eid]:
        collapsed[eid] = row  # last matching revision wins

# Step 3: Only production account id
env_id = "account-202"
collapsed = [v for v in collapsed.values() if v["customer_id"] == env_id]

# Step 4: Only status=settled
collapsed = [v for v in collapsed if v["status"] == "settled"]

# Step 5: Filter date range boundaries
# 2026-05-01T00:00:00Z <= occurred_at < 2026-06-01T00:00:00Z
start_utc = datetime(2026,5,1,0,0,0,tzinfo=timezone.utc)
end_utc = datetime(2026,6,1,0,0,0,tzinfo=timezone.utc)

def parse_dt(d):
    try:
        return datetime.fromisoformat(d.replace("Z", "+00:00"))
    except Exception:
        return datetime.strptime(d, "%Y-%m-%dT%H:%M:%S%z")

collapsed = [v for v in collapsed if start_utc <= parse_dt(v["occurred_at"]) < end_utc]

# Step 6: Sum amount_minor per currency, refund is subtract, capture is add
totals_minor = {}
included_event_ids = []
for v in collapsed:
    cur = v["currency"]
    amt = v["amount_minor"]
    if v["kind"] == "refund":
        amt = -amt
    if cur not in totals_minor:
        totals_minor[cur] = 0
    totals_minor[cur] += amt
    included_event_ids.append(v["event_id"])

included_event_ids = sorted(list(set(included_event_ids)))

result = {
    "totals_minor": totals_minor,
    "included_event_ids": included_event_ids
}

with open("report.json", "w") as f:
    json.dump(result, f, indent=2)
'
