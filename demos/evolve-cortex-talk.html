Agents that learn from their mistakes

Learned guidelines with ALTK-Evolve, and what changes when they live in the proxy in front of every coding agent.

Work in progress · Nov 2026
The problem

Agents have amnesia

Every session starts from zero

What the agent worked out yesterday about this repository, these tools, this environment, is gone when the session ends.

They don't learn from mistakes

The same error is made again in the next session, by the next developer, on the next agent. Each time it costs steps, tokens and review.

Possible approaches

Three ways to stop repeating mistakes

Fine-tune

  • Collect trajectories, fine-tune a model
  • Maybe with RL techniques

Needs a dataset, reward models, fine-tuning and deploying the model. Not possible for models we don't own.

Context engineering

  • Put previous error traces into the context
  • Hope the agent learns to avoid them

Long, noisy context. The agent has to work out the lesson again in every session.

Learned guidelines

  • Learn the lessons from trajectories
  • Apply them to the context of later tasks

The approach we took. No weights change, works with any model, every lesson is readable and reviewable.

ALTK-Evolve

Design questions we're working through

What should a guideline say?

  • Scope: general advice, or facts about this repository?
  • Rule or recovery: tested, state the rule (slide 14)

Who decides it's good?

  • Review: a person, or Cortex measuring sessions with and without it
  • Where: in Evolve, in Cortex's UI, or both

When?

  • Learn: on idle today; or at session end, a commit, a PR
  • Retrieve: once per session, or when the task changes

Shared with whom?

  • Redaction before session content reaches Evolve
  • Sharing across people and teams

Demo · what Evolve learned

Two guidelines, from one session, with no feedback

  1. Before committing in this repository, update CHANGES.md by adding an entry under the ## Unreleased section describing the change, and bump clients/python/VERSION to the next minor version when a new field is added to the Python client.
  2. When adding a new field to a model, follow the four-step sequence: (1) edit schema/models.yaml, (2) run make generate, (3) run make migration NAME=<change>, (4) run make check && make test before staging.

About the repository, not the agent, so they can transfer.

What made the difference

Same session, two prompts

Default prompt

"Run all pre-merge checks (make check) before committing to discover hook requirements…"

"When a pre-commit hook rejects a commit…, address each message exactly as stated before retrying."

How to recover. No guideline names CHANGES.md.

rules prompt

"Before committing in this repository, update CHANGES.md… under ## Unreleased…, and bump clients/python/VERSION to the next minor version…"

The rule, as a step before the action. Opt-in setting; the default prompt is unchanged.

The rules prompt adds one instruction: when an error message states a requirement, write that requirement as a step to take before the action it blocked.
