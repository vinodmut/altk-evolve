Summary

The integration is a self-contained outbound plugin. All behaviour lives in core/plugins/evolve/. It uses only pipeline APIs that already exist on main and changes no file under core/pipeline, core/session, core/sessionapi or core/config. It does nothing until a pipeline config names it.

Changes outside the plugin, and why each is needed

None of these change behaviour. Each is the minimum the build system requires to compile an optional plugin into some binaries and not others.

1. cmd/cortex/plugins_evolve.go registration

+//go:build include_plugin_evolve
+
+package main
+
+import _ "github.com/rossoctl/cortex/core/plugins/evolve"

Why: plugins register themselves in an init(); the binary only links the ones it imports. This is the same five-line file every other plugin had on main at the time (plugins_inferencerouter.go, plugins_ibac.go, …), and the build tag keeps it out of any profile that doesn't list it.

Now: upstream has since moved these files to core/plugins/all/. This one should move with them before a PR (section 4).

2. scripts/profile-tags/profiles.go and its test registration

@@ var membership = map[PluginName][]ProfileName{
+	// Full only, like inference-router: it reaches laptops through the release tarballs
+	// and changes no traffic until a pipeline names it. It needs an altk-evolve MCP
+	// server beside it, which only a laptop runs today; only cmd/cortex registers it.
+	"evolve": {ProfileFull, ProfileFullCpex},

Why: profile membership decides which binaries get the build tag. The guard tests require every registered plugin to have an entry, and TestTags_ReproduceTodaysDefaults pins the expected tag list, so the test edit is the expected list gaining "evolve".

Why only full/fullcpex: it mirrors inference-router. Laptops get it through release tarballs, the sidecar images don't grow, and it is inert until configured. It is deliberately not in local, the desktop profile, so agentop setup users are unaffected.

3. core/go.mod dependency

+	github.com/mark3labs/mcp-go v0.43.2
  …
-	github.com/mark3labs/mcp-go v0.43.2 // indirect

Why: the plugin talks to Evolve's MCP server over SSE with mcp-go. That module, at the same version, was already in Cortex's module graph as an indirect dependency, so go.sum is unchanged and no new code enters the build. Only the direct/indirect marker moves.

Alternative considered: a hand-rolled SSE + JSON-RPC client. Rejected: more code to own, and MCP's session and keep-alive handling is easy to get subtly wrong.

Plugin design

Both calls go from the plugin to Evolve; Evolve never calls Cortex. ① runs on the request path, once per session, bounded by timeout_ms, and fails open. ② runs from a 30-second background ticker after the response is on the wire, so it never delays a request.

What it does on each request

  1. Eligibility. Only main-agent inference requests with tools, a session ID and an allowed client. It skips subagents, tool-less side calls (titles, summaries), unknown clients and its own calls (X-Evolve-Cortex header), recording a skip reason.
  2. Fetch once per session. On a session's first eligible request it asks Evolve for guidelines matching the task, the first user message with <system-reminder> removed. The result is cached per session (cache_ttl_seconds, default 30 min), with concurrent requests of one session waiting on a single fetch.
  3. Inject byte-stably. It appends one delimited <evolve-guidelines> block, rendered once and reused, so every turn adds identical bytes and the provider's prompt cache keeps hitting. Edits use sjson on the raw body, so cache_control markers and every untouched field survive byte for byte.
  4. Placement. system (default) adds a trailing system block; user puts the block in a <system-reminder> leading the first user message. user was added after an experiment showed the model ignored guidelines at the end of Claude Code's long system prompt.
  5. Attribute. Publishes plugins.evolve on the session event: whether it injected, guideline IDs, revisions and sources. agentop shows it in the detail pane.

What it does after each response

  • OnFinish records each successful main-agent turn into a per-session recorder. It only appends in memory, after the response is on the wire.
  • A background ticker (30 s) sends a session's new turns to Evolve's process_trajectory once it has been idle for idle_after_seconds, as one identified batch. Retried batches reuse their ID, so Evolve skips duplicates.

Configuration surface

Sixteen fields, all optional except endpoint, validated with DisallowUnknownFields. inject and learn each switch half of the plugin off; on_error: observe computes and publishes the event without changing bytes. Full table in docs/evolve-plugin.md.

Safety properties

PropertyHow
Fails openEvolve down, slow (timeout_ms, default 3 s, paid once per session) or erroring: the request goes upstream unchanged and fetch errors is counted. A panic in OnRequest is recovered and the original body forwarded. A session keeps its last good guidelines through a failed refresh.
Review gateLearned guidelines go to learn_namespace (default cortex-candidates), which is never injected from. Only serve_namespace (default cortex) is served, and config validation refuses the two being equal. A person promotes candidates by copying them across.
Prompt-injection containmentSession content includes tool output the agent read. Without the gate, text an attacker planted in a web page could become a permanent instruction. Conflict resolution also runs per namespace, so a learned trajectory can't rewrite a reviewed guideline.
Block can't be forgedGuideline text is stripped of anything resembling the block's open or close tag, so content can't end the block early or start a second one.
No learning loop on itselfRecorded turns have <system-reminder> and <evolve-guidelines> blocks removed, so Evolve never learns from its own injected text or harness context.
Its own traffic isn't recordedThe MCP client's transport has Proxy: nil, so it never goes back through Cortex as HTTPS_PROXY, and it sets X-Evolve-Cortex as a second guard.
Bounded memorymax_sessions (1024) caps cached and recording sessions; tool results are truncated to 4 KB and user text to 8 KB per message; pending messages per session are capped at 400.
Prompt cache intactByte-stable block, appended after any cache_control breakpoint, so the cached prefix is unchanged.
!

Known limits, documented in docs/evolve-plugin.md. Evolve's MCP server has no authentication, so it must bind to loopback on a single-user machine. A shared or remote Cortex needs an authenticated Evolve first. Unsent turns are in memory and are lost on restart. Session content goes to Evolve's LLM unredacted unless Evolve's own hooks are configured.

Asks and open questions

For the Cortex team

  1. Is a plugin in the main repo the right home? Or would you rather it live out of tree? It has no core dependencies beyond the plugin contract.
  2. Profile membership: is full/fullcpex right, or should it stay out of every default profile until it leaves Alpha?
  3. Default placement: should placement: user become the default? Results so far favour it: in a 28-session experiment, wrong-path reads fell from 6/11 to 0/11. But it edits user content rather than system instructions, which you may prefer to keep opt-in.
  4. Session archive location (#1689): would make side-by-side and demo setups much simpler, without touching the plugin.
  5. Ordering with context-guru: it can compact the injected block away. Is "place evolve after it" in the docs enough, or should the plugin declare an ordering?

Design of the loop

  1. Should there be a manual review gate, or should learnings apply automatically?
    Today: manual. Nothing learned is injected until a person copies it from cortex-candidates to cortex.
    Trade-off: the gate stops text from tool output (a fetched web page, a file the agent read) becoming a standing instruction for every later session, which is the main prompt-injection risk. It also costs a person's attention, and in the experiments some candidates were generic and worth rejecting. Automatic application would need another safeguard: shadow A/B gating (below), automatic expiry, or a trust signal on where the content came from.
  2. Should the manual review happen in Cortex or in Evolve?
    Today: in Evolve. The plugin only reads and writes Evolve namespaces; review is an Evolve CLI copy between them.
    Trade-off: in Evolve, the review is the same for every client of Evolve, not just Cortex, and Cortex stays a thin client. In Cortex, it could sit in agentop next to the session a candidate came from, so a reviewer sees the evidence and approves in one place, but Cortex would then own guideline state. A middle option: agentop shows candidates and their source sessions, and the approve action calls Evolve.
  3. Should trajectories be sent on idle, or at some other time?
    Today: after a session has been idle for idle_after_seconds (default 15 minutes), checked every 30 seconds; a resumed session later sends only its new turns.
    Trade-off: idle is a cheap signal that a task is probably finished, needs nothing from the agent, and batches the turns. But it is a guess: a long pause mid-task splits one task in two, and turns not yet sent are lost if Cortex restarts. Alternatives: on an explicit signal (session end, the agent's own "done", a commit or a PR), on a turn or size threshold, or at a fixed time.
  4. Should guidelines be retrieved once per session, or at another granularity?
    Today: once, matched to the session's first user message, then cached for cache_ttl_seconds so every turn adds identical bytes and the prompt cache keeps hitting.
    Trade-off: once per session is cheap and cache-friendly, but a session that changes task midway keeps guidelines chosen for its opening message. Finer options cost cache hits or need a trigger: per user turn (re-match when the user gives a new instruction), just-in-time (add a guideline on the request after a tool error matching its trigger), or per tool (attach guidance to the tool about to be used).

Not yet built

  • Shadow A/B gating: inject a candidate on a fraction of sessions and promote it only when outcomes improve. This would replace manual promotion.
  • Redaction of session content before it reaches Evolve, and learning from subagent trajectories.
  • Just-in-time injection: add a guideline on the request after a tool error that matches its trigger.
