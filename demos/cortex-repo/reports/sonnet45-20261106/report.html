Evolve learns a repository's conventions

Can Evolve learn a repository's unwritten rules from one ordinary Claude Code session, with nobody grading or correcting it, so that the next sessions stop running into them?

Partly. Every baseline run had its commit rejected twice. With Evolve's learned guidelines injected, 2 of 6 runs committed first time and rejections fell from 12 to 7. Correctness tied (6/6 each) and cost was flat. Why it is not larger: the guidelines told the agent how to react to a rejection, not what the rules were.

The setup

A small schema-driven Python library, shopkit, whose git hooks reject a commit unless it has regenerated code and a migration, an entry in CHANGES.md, a bump of clients/python/VERSION, and a lower-case Conventional Commit subject. The task prompt mentions none of this.

1 · TrainAdd users.nickname. Cortex records the session.
2 · LearnEvolve reads the recorded session. No feedback, no grade.
3 · ReviewA person promotes 4 of 5 candidates.
4 · Evaluate6 baseline/guided pairs on 3 different fields, interleaved.
5 · GradeAn offline grader checks each committed repository.

Everything ran in Docker: Claude Code 2.1.287, Cortex (placement: user), Evolve, the repository and its toolchain. Task and learner model aws/claude-sonnet-4-5. Every session starts from a fresh clone.

What happened in training

The training session succeeded after 2 rejected commits (40 tool calls, $0.19). That is the only evidence Evolve had:

  1. ✕ rejected Add optional nickname field to users
    • pre-commit: schema/models.yaml changed without an entry in CHANGES.md under '## Unreleased'
    • pre-commit: clients/python/shopkit_client.py changed; bump clients/python/VERSION (minor for a new field)
    • pre-commit: commit rejected
  2. ✕ rejected Add optional nickname field to users
    • commit-msg: subject must be a Conventional Commit in lower case, e.g. 'feat(users): add nickname'
  3. ✓ accepted feat(users): add optional nickname field

What Evolve learned

  • promoted For code generation systems, always modify the source schema first, then run the generation tool, rather than manually editing generated files
  • promoted When commit hooks reject a commit, read the error message to identify all required companion changes (changelog, version bumps, commit format) before re-attempting
  • promoted For schema changes that add database columns, use the repository's migration tool to auto-generate the migration rather than writing SQL manually
  • promoted After making changes to a schema-driven system, run the repository's consistency check tool before committing to catch mismatches between schema and derived artifacts
  • not promoted For repositories with semantic versioning requirements, determine the version bump type (major/minor/patch) based on the nature of the change before modifying VERSION files
    Generic semantic-versioning advice; the session only showed that the client VERSION must change, which candidate 2 covers.
First learning pass, discarded

Evolve renders the first 50 steps of a session by default. Training ran 61 steps, so the second rejection and the recovery were cut off, and the first pass learned nothing about the hooks. The demo now renders 150 steps.

  • When modifying a code generation system, always identify and update the source schema file first, then use the project's build system to regenerate derived files rather than editing generated files directly
  • For schema changes that affect databases, create a migration file after updating the schema and regenerating code, using the project's migration tooling if available
  • Before committing changes, run all project validation tools (check, test, lint) and review their output to catch configuration requirements like commit message formats
  • When exploring a new codebase to understand how to add a feature, examine the schema/config files, generated code, and existing tests in that order to understand the full data flow
  • After making changes to a code generation system, verify the changes work correctly by writing and running manual tests that exercise the new functionality through the full stack (model creation, persistence, retrieval, and client validation)

Why the effect is modest

  • The lesson that would help most was generalised away. Evolve learned "when commit hooks reject a commit, read the error for all required companion changes". That is advice for after a rejection. It never stated the rules themselves, so four of six guided runs still had to be rejected once to discover them. Evolve's prompt asks for general guidelines without task-specific values, which strips out exactly the repository-specific facts that would prevent the error.
  • The hooks force correctness. A run cannot finish without fixing its commit, so both arms always pass. The benefit can only show up as avoided rejections.
  • Six pairs is a small sample. The direction is consistent (no guided run did worse than its baseline), but the size is not established.

Next

  • Let Evolve keep concrete facts scoped to a repository: "in this repository, a schema change needs a CHANGES.md entry, a clients/python/VERSION bump, and a lower-case Conventional Commit subject". Rerun the six pairs.
  • Raise Evolve's default 50-step window for Cortex coding sessions, so lessons at the end of a session are not cut off.

Method and limits

  • Baseline and guided alternate, and so does the arm that runs first. Each pair uses the same field; pairs rotate through three fields.
  • Guidelines were frozen before any evaluation session and injected on the first user message of every guided session (ids 1–4, verified on each session's first request). No baseline received them.
  • A rejected commit is a failed git commit whose output contains a hook message. Reading the hook scripts does not count.
  • The grader copies each repository into a network-disabled container and checks: clean tree, a new commit, the pre-merge check, migrations apply and add the column, a value stored and loaded back, the test suite, the changelog entry, the client version bump, and Conventional Commit subjects.
  • One model, one repository, six pairs. Costs are Claude Code's reported totals; they exclude Evolve's learning call.
