Why this matters

Each coding-agent vendor is building memory into its own tool, for its own users. This probe is the first evidence for the argument that a layer we control can do something theirs can't: knowledge one agent works out is used by a different agent, from a different vendor, running a different model.

The lessons here are about the repository, not the agent: "this repository needs a CHANGES.md entry and a client version bump". That is exactly the kind of knowledge that should transfer, and it did.

2

What was learned, from Claude Code

The Claude Code training session (83c7705a) had its first commit rejected for the missing changelog entry and version bump, fixed both and committed. Cortex sent the session to Evolve after it went idle; Evolve learned four candidates with no grading or feedback. All four were promoted:

2. Before modifying any field or schema, identify whether the repository uses a code-generation pattern (a source-of-truth schema file that generates derived files) and use the provided generation tooling rather than hand-editing generated files.
3. After updating a schema, create the corresponding database migration file following the repository's established naming and content conventions.
4. Read and satisfy all pre-commit hook requirements (changelog entries, version bumps, generated-code checks) before attempting to commit, to avoid a rejected commit and the need for a second commit.
5. Proactively check whether a repository has a CHANGES.md (or CHANGELOG) and a client version file and update both when adding a user-facing field, even before the first commit attempt.

None names a Claude-specific tool, which is part of why they can transfer.

The guided session didn't open .githooks/, as Claude Code's guided runs did. It went straight to the files guideline 5 names, updated both before its first commit, and wrote a Conventional Commit subject. Its final message doesn't mention the guidelines; the change in behaviour is the evidence.

Caveats

  • One pair. Earlier Claude Code runs varied a lot between identical sessions. This is a signal to measure, not a measured effect.
  • The guided session got the version bump wrong in kind. It bumped the client from 1.3.0 to 1.3.1 (patch). The hook's message asks for a minor bump for a new field, and the baseline, which saw that message, bumped to 1.4.0. The hook only checks that the version changed, so it accepted 1.3.1, and the grader passed it for the same reason. The guideline says "update both" without saying how; Evolve generalised away the "minor for a new field" detail. This is the known weakness of generic guidelines, now shown on a second agent.
  • Same task family as training. Both are "add a field" tasks on the same repository, with a different field and model. This tests transfer across agents, not across task types.
  • One discarded run. The first Codex baseline ran in Codex's default sandbox, which made .git read-only, so it could not commit at all. It is kept as codex-baseline-1-sandboxed and excluded. Both reported runs used the same permissions.
  • Different model families. Codex used a GPT model, Claude Code a Claude model. Only Codex baseline and Codex guided are compared with each other.
