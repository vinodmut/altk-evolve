One lesson, end to end

A real recorded run: a coding agent gets its commit rejected, Cortex records it, Evolve turns it into a guideline with nobody grading anything, a person approves it, and Cortex hands it to a new session doing a different change. That session reads the hooks first and commits on the first try.

The setup

shopkit is a small Python library. Its git hooks reject a commit unless it has a CHANGES.md entry, a bump of clients/python/VERSION, and a lower-case Conventional Commit subject (feat(users): …). The task prompt mentions none of this.

Every session runs in a fresh clone, through Cortex with the evolve plugin (placement: user). Learning was triggered on the training session only; nothing from the evaluation sessions was learned.

2
Cortex · evolve plugin

Cortex records the session

On every successful main-agent turn, OnFinish folds the request's new messages, the reply, its tool calls and the next request's tool results into OpenAI chat messages, after the response is already on the wire. Errors are marked [error], so the two rejections above are in the record exactly as the agent saw them.

When the session goes idle, the plugin sends its new turns to Evolve's stock process_trajectory tool as one identified batch, cortex:b590c2fc…:64. A retry reuses the ID, so Evolve won't learn the same turns twice.

i

Cortex strips <system-reminder> and <evolve-guidelines> blocks from what it records, so Evolve never learns from harness context or from its own earlier output.

3
Evolve

Evolve learns, with no grading

Evolve's learner reads the whole recorded session: every action paired with its result. Nobody says whether the run succeeded; the only signal is what happened. It wrote five candidates into the cortex-candidates namespace. The one tied to the rejections:

When commit hooks reject a commit, read the error message to identify all required companion changes (changelog, version bumps, commit format) before re-attempting
FieldWhat Evolve recorded
Rationale"The agent initially committed without updating CHANGES.md or VERSION, triggering a pre-commit hook rejection. Then updated those files but still failed due to incorrect commit message format. Reading all hook requirements upfront would have avoided multiple failed commit attempts."
Categoryrecovery
Provenancesession b590c2fc…, batch cortex:b590c2fc…:64
!

The first attempt at learning saw nothing about the hooks. Evolve renders at most 50 steps of a Cortex session (the first 40 and last 10), which dropped step 30's rejection. The demo raises the limit to 150.

4
A person

A person reviews and promotes

Nothing learned is served until someone copies it from cortex-candidates to the served namespace, cortex. This is the plugin's review gate. Session content includes tool output the agent read, so without it, text from a web page could become a permanent instruction.

Four of the five candidates were promoted unchanged:

  1. For code generation systems, always modify the source schema first, then run the generation tool, rather than manually editing generated files
  2. When commit hooks reject a commit, read the error message to identify all required companion changes (changelog, version bumps, commit format) before re-attempting
  3. For schema changes that add database columns, use the repository's migration tool to auto-generate the migration rather than writing SQL manually
  4. After making changes to a schema-driven system, run the repository's consistency check tool before committing to catch mismatches between schema and derived artifacts

The fifth, generic semantic-versioning advice, was left out.

Cortex · evolve plugin

Cortex injects them into a new session

A fresh session gets a different task: add locale to users. On its first request the plugin asks Evolve for guidelines matching the task, caches the answer for the session, and puts them in a <system-reminder> at the start of the first user message. Every later turn adds the same bytes, so the prompt cache keeps working.

Both repositories pass the offline grader: committed, pre-merge check passes, the migration adds the column, a value round-trips through the library and client, tests pass, and the changelog, client version and commit subject are right.

What this doesn't show

  • This is the best pair, not the average. Across six recorded pairs, 2 of 6 guided runs committed first time against 0 of 6 baselines; rejected commits went from 12 to 7, and median cost and tool calls were flat. See the full report.
  • The guideline is reactive. It says what to do after a rejection; this agent chose to apply it up front by reading the hooks. Four of six guided runs still had to be rejected once. A guideline that stated the rules themselves ("this repository requires a CHANGES.md entry…") would likely do better. Evolve's prompt currently generalises those specifics away.
  • Correctness can't improve here: the hooks force every run to finish correctly, so the benefit shows up only as fewer wasted steps.
