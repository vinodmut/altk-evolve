Evolve in Cortex: what only a proxy can offer

Each agent vendor is building memory into its own tool. Cortex sits in front of all of them: every agent, every model, every user, with their tool results, costs and policy decisions in one place. These are the uses of Evolve that come from that position, and that no single vendor's memory can match. None of them asks developers to grade, give feedback or change how they work.

The position

A vendor's memory sees one agent, one model and one user's sessions. Cortex sees the traffic itself, which gives Evolve four things to work with that a vendor doesn't have:

Every agent and model

Claude Code, Codex, opencode, Bob and subagents, on whatever model each is routed to.

Every user, eventually

One shared Cortex means one developer's lesson can reach a whole team.

Outcomes, for free

Tool results, rejected commands, policy denials, tokens and cost, already recorded per session.

Control of delivery

Cortex decides which sessions get which guidelines, so it can also hold some back and compare.

The angles below are grouped by what that buys: who learns from whom, what there is to learn from, and why the result can be trusted.

Who learns from whom

0 · Across agents shown, one pair

What Claude Code works out, Codex already knows.

Guidelines Evolve learned from a Claude Code session were injected into a Codex session on a different model and a different change. Codex's rejected commits went 2 → 0, tool calls 13 → 8 and input tokens −39%. This is the anchor for everything below: guidelines belong to the repository, not to the agent. Full report.

1 · Across models recommended

Change models without losing what was learned. A strong model teaches; a cheaper one does the work.

The problem
Teams change models every few months, for cost or capability. The new model, especially a cheaper one, often makes mistakes the old one had stopped making, and a vendor's memory doesn't carry across that change.
Why Cortex
Guidelines live in Cortex, not in a model or an agent. Cortex's inference-router plugin already chooses which inference server each agent's sessions go to, so a model change happens at the same place the guidelines are delivered.
Evidence today
The Codex probe already used a weaker model (gpt-5.6-luna) helped by guidelines learned on a stronger one (Sonnet 4.6). That is one data point for "strong teaches, cheap works".
To show it
Same agent, same task, two models: learn on the stronger model, then run the cheaper one with and without the guidelines. The claim to test is "the cheaper model with guidelines matches the stronger model without them" on rejected commits and cost per task.
Why it lands
It's a cost story with a number attached: the cost of each task on the cheaper model, with guidelines, against the stronger one.

2 · Across people

One developer's agent hits a convention once; everyone's agent knows it the next session.

The problem
Repository knowledge stays in individual sessions. Every developer's agent pays for the same mistake separately, and a new hire's agent starts from nothing.
Why Cortex
A shared Cortex sees every developer's sessions. A vendor's memory is per user, or at most per vendor account.
A by-product
Across many repositories, the guidelines form a map of which conventions agents keep tripping on: undocumented team knowledge, made visible. It's useful for documentation and onboarding even without agents.
To show it
Needs a shared Cortex and namespaces keyed by repository, not by machine. Two simulated users on one repository is enough for a first demo.
Needs first
Authentication and redaction: a guideline learned from one person's session should never carry their data to someone else. These are already on the open security list.

3 · Within a workflow

The review agent's finding becomes the coding agent's guideline.

The problem
Developers increasingly run several agents together: a coding agent, subagents, a review or test agent, agents in parallel on the same repository. What one of them finds, the others don't learn.
Why Cortex
Cortex sees all of their traffic, including agent-to-agent calls (the a2a-parser plugin). Each agent alone sees only its own conversation.
To show it
A review agent flags the same problem in two coding sessions; Evolve learns from the review sessions; the third coding session avoids it.

What there is to learn from

4 · From what Cortex blocked

Every request Cortex blocks is a lesson that cost nobody any effort to label.

The problem
When a guardrail blocks an agent, the agent retries, works around it, or stops, and does the same next session. Repeated friction is also what pushes teams to loosen a policy.
Why Cortex
Cortex is where the denials happen: ibac denies outbound calls that don't match the user's intent, opa applies policy, session-budget enforces token and call limits, and sparc reflects on tool calls before they run. Each decision is a clear failure signal, already recorded.
To show it
Feed denials into the trajectory Evolve learns from (or as a separate signal), so it learns "in this repository, don't call X; use Y". Then count how often agents hit the same denial before and after.
Why it lands
It's the angle most specific to Cortex, and the strongest reason for the Cortex team to want the plugin: it makes their guardrails cause less friction without making them weaker.

5 · From waste

The proxy that meters every token learns where they're wasted.

The problem
A lot of agent spend goes to loops: reading the same file again and again, retrying a failing command, long detours. Nobody reviews sessions for this.
Why Cortex
Cortex already records tokens, cost and every tool call per session. Its tool-prune and context-guru plugins already cut the size of each request; guidelines would cut the number of steps.
Evidence today
The Codex pair used 39% fewer input tokens; the best Claude Code pair went from $0.32 to $0.19. Both came from avoiding rework, not from guidelines aimed at waste.
To show it
Point learning at the most wasteful sessions (most repeated calls or tokens per change) and report cost per task before and after.
Why it lands
"The proxy pays for itself" is the easiest of these to fund.

Why the result can be trusted

6 · Measured automatically recommended

Cortex holds guidelines back from a small share of sessions, and the difference is the measurement.

The problem
Every result so far is a small, hand-run experiment. Reviewing each guideline by hand doesn't scale, and leadership's first question is "is the gain real?"
Why Cortex
Cortex decides delivery and already records which guidelines each session received. Holding some sessions back is a config decision, not an experiment someone runs.
What it enables
Compare rejected commits, tool calls and cost between sessions with and without each guideline. Promote what measurably helps; retire what doesn't. That replaces the manual review step with evidence, which is open design question 6 in the change review.
To show it
A holdout setting in the plugin plus a per-guideline report from session data already recorded. It is the measurement the pilot needs anyway.

7 · Kept current

A guideline that stops matching the repository gets noticed, because Cortex sees what happens next.

The problem
Hand-written instruction files go stale and nobody notices until an agent does the wrong thing confidently.
Why Cortex
Cortex sees the results of sessions that received a guideline. If those sessions start failing in a new way (a hook was removed, a command renamed), the guideline is the suspect.
To show it
Change a hook in the sample repository after learning; show the guideline flagged for review or retired. Builds on angle 6's per-guideline data.

8 · Kept local

Learning that never leaves infrastructure we run.

The problem
Some teams can't send sessions to a vendor's memory feature, so they get no learning at all.
Why Cortex
Cortex and Evolve run where we run them, with the model we choose. Redaction at the proxy is a single choke point for every agent.
Why it lands
It turns the open security items (authentication, redaction, data handling) from a weakness into the pitch for regulated teams.

Recommendation

  1. Across models (1). It reuses the Codex probe setup, gives a cost number leadership can check, and needs no new Cortex code.
  2. Measured automatically (6). It answers "is the gain real?" with real sessions instead of hand-run experiments, and it's what the pilot needs to report results.
  3. From what was blocked (4), to raise with the Cortex team. It's the angle that most clearly needs Cortex, and gives them a reason of their own to want the plugin.
