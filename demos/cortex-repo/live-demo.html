Live demo runbook

Evolve in Cortex, live: learn from one agent, help another

Two demos of the same repository with rules no prompt mentions. In the first, Claude Code makes a mistake, Evolve learns from it, you promote what it learned, and Codex benefits. In the second, Codex runs twice, without and with guidelines loaded from a file. Every step is one script.

Which flow

Flow 1 · Claude Code → CodexThe whole loop live: a Claude Code session is rejected by the repository's hooks, Evolve learns from it with no feedback, you promote the guidelines, and Codex does a different change without that mistake. Shows learning, the review gate and transfer across agents. Flow 2 · Codex → CodexLearning skipped: the same Codex task twice, first with no guidelines, then with guidelines loaded from a file. Shorter and more predictable; shows only the effect.

Both use shopkit, whose git hooks reject a commit that changes the schema unless CHANGES.md has an entry under ## Unreleased, clients/python/VERSION is bumped, and the subject is a Conventional Commit.

once

This runbook assumes the setup from the manual walkthrough: $WALK/env.sh, Evolve's MCP server (port 8201 there), a dev Cortex with the evolve plugin (47700 and 47701 there), $WALK/claude-dev.json, and the shopkit virtualenv. Two additions:

Codex through the dev Cortex

once · 5 min

Codex gets its own CODEX_HOME, whose .env points it at the dev Cortex, and its own HOME, so none of your personal skills or settings reach the demo. Its .env wins over the shell's proxy variables, so your everyday Codex is unaffected.

mkdir -p "$WALK/codex-home" "$WALK/codex-user"
cat > "$WALK/codex-home/config.toml" <<EOF
model_provider = "walk_litellm"
model = "azure/gpt-5.6-luna"
approval_policy = "never"
sandbox_mode = "danger-full-access"

[model_providers.walk_litellm]
name = "LiteLLM via dev Cortex"
base_url = "$LITELLM_URL/v1"
wire_api = "responses"
env_key = "WALK_LITELLM_KEY"
supports_websockets = false

[features]
skill_search = false
memories = false
plugins = false
hooks = false
apps = false
multi_agent = false

[projects."$WALK/live/shopkit"]
trust_level = "trusted"
EOF
umask 077; cat > "$WALK/codex-home/.env" <<EOF
WALK_LITELLM_KEY=$LITELLM_KEY
HTTPS_PROXY=http://127.0.0.1:${CORTEX_PROXY:-47700}
HTTP_PROXY=http://127.0.0.1:${CORTEX_PROXY:-47700}
SSL_CERT_FILE=$WALK/cortex-home/.cortex/ca/bundle.crt
EOF
printf 'export PATH="%s/shopkit-venv/bin:$PATH"\n' "$WALK" > "$WALK/codex-user/.zprofile"
printf '[user]\n\tname = shopkit agent\n\temail = agent@shopkit.test\n[init]\n\tdefaultBranch = main\n' > "$WALK/codex-user/.gitconfig"
  • Model: any Responses-API model your key serves. The rehearsal used azure/gpt-5.6-luna, which reliably makes the mistake without guidelines.
  • danger-full-access: Codex's default sandbox makes .git read-only, so it couldn't commit. The demo repository is a throwaway clone.
  • Session grouping: Codex names its session in a Session-Id header. Add it to the dev Cortex's session.id_headers list, next to X-Session-Id, and restart the dev Cortex (this setting isn't hot-reloaded).

Check it once:

./reset.sh
./codex.sh exec "Reply with exactly: READY" < /dev/null
curl -s --noproxy '*' "127.0.0.1:${CORTEX_API:-47701}/v1/sessions?archived=true" | jq -r '[.sessions[] | select(.agent=="codex")] | max_by(.createdAt) | .id'
✓

READY, then a session ID: the dev Cortex recorded the Codex session.

Interactive ./codex.sh hands each prompt to a background Codex process, one per CODEX_HOME, so the demo's is separate from your everyday Codex's. It reads codex-home/.env only when it starts. If you change that file, restart it:

env -u HTTPS_PROXY -u HTTP_PROXY HOME="$WALK/codex-user" CODEX_HOME="$WALK/codex-home" codex app-server daemon restart

Flow 1 · Claude Code → Codex

~8 min

1.1 Prepare before you start talking

./prepare.sh          # guidelines on, learning on, 30 s idle, empty namespaces
./reset.sh            # fresh shopkit with one commit
✓

Cortex evolve plugin: {"inject":true,"learn":true,"idle_after_seconds":30} and Served guidelines and candidates cleared. Cortex sends a session to Evolve once it has been quiet for 30 s, down from 90, so the demo doesn't wait.

1.2 Claude Code does the source task ~2 min

./claude.sh

Paste the Claude Code prompt. When it has printed its summary, type /exit.

!

The first time Claude Code opens the demo repository, it asks whether you trust the folder, and the highlighted default is No, exit. Press ↓ then Enter for "Yes, I trust this folder". It remembers the path, and reset.sh recreates the repository at the same path, so answer it during the rehearsal and it won't ask on stage.

It does the change well. Now watch the commit: the repository's hooks reject it for two rules nobody told it about. It reads the error, fixes both, and commits again.
✓

   - `schema/models.yaml changed without an entry in CHANGES.md under '## Unreleased'`

8. Fixed by editing `CHANGES.md` …
9. Fixed by editing `clients/python/VERSION` — bumped `1.3.0` → `1.4.0` …
10. Re-ran `git commit` — all 6 files committed successfully

1.3 Watch Evolve learn ~1 min

./candidates.sh wait
Nobody graded that session or gave feedback. Cortex saw it go quiet, sent it to Evolve, and Evolve is working out what to learn from the rejection.
✓

A table of candidates, about 45 s after the session ended in the rehearsal. IDs keep counting across runs, so use the ones shown. To read one in full, with its trigger, rationale and source session: ./candidates.sh show <id>. The rehearsal learned:

[3] Before committing changes to `schema/models.yaml` or `clients/python/shopkit_client.py`, add an entry
    under `## Unreleased` in `CHANGES.md` and bump `clients/python/VERSION` (minor version for a new field).
[4] In the shopkit repository, follow the full four-step pipeline when adding a field to a model: (1) edit
    `schema/models.yaml`, (2) run `make generate`, (3) run `make migration NAME=<name>`, (4) run `make test`.
[5] When adding an optional field to a model in shopkit, declare it with `{type: str}` …

1.4 Promote them ~30 s

./promote.sh 3 4 5        # the IDs from the table
./guidelines.sh list
This is the review gate. What Evolve learns is only a candidate. Nothing reaches an agent until a person promotes it, so a web page an agent read can't become a standing instruction.
✓

Imported into 'cortex' with one ADD per guideline, each keeping its source session as provenance.

./codex.sh

Different vendor, different model, different change. It has never seen this repository, but its first request carries what Claude Code's session taught. Watch for CHANGES.md and VERSION before its first commit.

Show the evidence

To prove where the change came from, open the dev Cortex in agentop in terminal C:

agentop observe -endpoint "http://127.0.0.1:${CORTEX_API:-47701}"
  • Open the guided Codex session and its first request. The evolve plugin's entry shows injected: true and the guideline IDs. The request's first user message starts with the <evolve-guidelines> block.
  • The timeline shows each command with its output, including the hooks' messages under a rejected commit.
  • From the command line instead: ./guidelines.sh list for what is served, ./candidates.sh list for what was learned.

Fallbacks

IfThen
./candidates.sh wait takes too long or learns nothing useful./guidelines.sh load serves the recorded guidelines from the same kind of session; carry on with 1.5.
Interactive Codex doesn't reach the dev Cortex./codex.sh exec "<prompt>" < /dev/null runs the same session non-interactively and streams every command.
Network or model troublePresent the recorded run: slides 11–15 of the talk, and the timelines in reports/loop-rules-20261111/.
You'd rather turn guidelines off at the proxy than empty the namespace./inject.sh off / ./inject.sh on switch the dev Cortex in about half a second, between sessions.

Troubleshooting

  • No candidates. The dev Cortex log should show evolve: sent idle session to learn from about 30 s after the session's last request. If it shows sending session to learn from failed, check the Evolve server's log for the model error. A config change, including ./inject.sh or ./prepare.sh, drops a session that hasn't been sent yet, so don't switch anything between 1.2 and 1.3.
  • Guidelines not injected. ./inject.sh status should say ON and ./guidelines.sh list should list them. Guidelines are fetched once per session, so start a new Codex session after loading.
  • No hook rejections at all. The hooks run Python from the shopkit virtualenv. Check $WALK/codex-user/.zprofile puts it on PATH, and that ./reset.sh set core.hooksPath.
  • Interactive Codex answers but no session appears in the dev Cortex. Its background process started before codex-home/.env pointed at the dev Cortex: restart it (command).
  • Claude Code exits straight away. The trust dialog's default is "No, exit"; choose "Yes, I trust this folder".
  • Codex runs but Cortex shows a pending:codex@… bucket instead of a session: add Session-Id to session.id_headers and restart the dev Cortex.

Script reference

In demos/cortex-repo/live/. Source env.sh first. Paths can be overridden with EVOLVE_ENV_FILE, CORTEX_CONFIG, CODEX_HOME_DIR, CODEX_USER_HOME and DEMO_REPO.

ScriptDoes
prepare.sh [idle]Sets the evolve plugin to inject and learn with a short idle wait (default 30 s), and empties cortex and cortex-candidates.
reset.shA fresh shopkit at $WALK/live/shopkit with one commit and its hooks enabled.
claude.sh / codex.shStart the agent in the demo repository through the dev Cortex. Extra arguments are passed on (for example exec "…").
candidates.sh list | show <id> | wait [s] | clearWhat Evolve learned; wait polls until new candidates appear.
promote.sh <id>…Copies candidates into the served namespace with their metadata (evolve entities export → import --append).
guidelines.sh list | clear | load [file]What the dev Cortex serves; load replaces it from a file (default guidelines/rules-20261111.json).
inject.sh on | off | statusSwitches injection in the dev Cortex through its config hot-reload.
