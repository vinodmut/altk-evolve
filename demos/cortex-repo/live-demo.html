Live demo runbook

Evolve in Cortex, live: learn from one agent, help another

Two demos of the same repository with rules no prompt mentions. In the first, Claude Code makes a mistake, Evolve learns from it, you promote what it learned, and Codex benefits. In the second, Codex runs twice, without and with guidelines loaded from a file. Every step is one script.

Which flow

Flow 1 · Claude Code → CodexThe whole loop live: a Claude Code session is rejected by the repository's hooks, Evolve learns from it with no feedback, the guidelines go live, and Codex does a different change without that mistake. Shows learning and transfer across agents, and optionally the review gate. Flow 2 · Codex → CodexLearning skipped: the same Codex task twice, first with no guidelines, then with guidelines loaded from a file. Shorter and more predictable; shows only the effect.

Both use shopkit, whose git hooks reject a commit that changes the schema unless CHANGES.md has an entry under ## Unreleased, clients/python/VERSION is bumped, and the subject is a Conventional Commit.

Codex through the dev Cortex

Codex gets its own CODEX_HOME, whose .env points it at the dev Cortex, and its own HOME, so none of your personal skills or settings reach the demo. Its .env wins over the shell's proxy variables, so your everyday Codex is unaffected.

mkdir -p "$WALK/codex-home" "$WALK/codex-user"
cat > "$WALK/codex-home/config.toml" <<EOF
model_provider = "walk_litellm"
model = "azure/gpt-5.6-luna"
approval_policy = "never"
sandbox_mode = "danger-full-access"

[model_providers.walk_litellm]
name = "LiteLLM via dev Cortex"
base_url = "$LITELLM_URL/v1"
wire_api = "responses"
env_key = "WALK_LITELLM_KEY"
supports_websockets = false

[features]
skill_search = false
memories = false
plugins = false
hooks = false
apps = false
multi_agent = false

[projects."$WALK/live/codex-shopkit"]
trust_level = "trusted"
EOF
umask 077; cat > "$WALK/codex-home/.env" <<EOF
WALK_LITELLM_KEY=$LITELLM_KEY
HTTPS_PROXY=http://127.0.0.1:${CORTEX_PROXY:-47700}
HTTP_PROXY=http://127.0.0.1:${CORTEX_PROXY:-47700}
SSL_CERT_FILE=$WALK/cortex-home/.cortex/ca/bundle.crt
EOF
printf 'export PATH="%s/shopkit-venv/bin:$PATH"\n' "$WALK" > "$WALK/codex-user/.zprofile"
printf '[user]\n\tname = shopkit agent\n\temail = agent@shopkit.test\n[init]\n\tdefaultBranch = main\n' > "$WALK/codex-user/.gitconfig"
  • Model: any Responses-API model your key serves. The rehearsal used azure/gpt-5.6-luna, which reliably makes the mistake without guidelines.
  • danger-full-access: Codex's default sandbox makes .git read-only, so it couldn't commit. The demo repository is a throwaway clone.
  • Session grouping: Codex names its session in a Session-Id header. Add it to the dev Cortex's session.id_headers list, next to X-Session-Id, and restart the dev Cortex (this setting isn't hot-reloaded).

Check it once:

./reset.sh
./codex.sh exec "Reply with exactly: READY" < /dev/null
curl -s --noproxy '*' "127.0.0.1:${CORTEX_API:-47701}/v1/sessions?archived=true" | jq -r '[.sessions[] | select(.agent=="codex")] | max_by(.createdAt) | .id'

          endpoint: http://127.0.0.1:8211/sse

          # Only guidelines promoted here are injected into agents' requests.
          serve_namespace: cortex
          agents: [claude-code, codex]
          placement: user
          …

./candidates.sh works on the learn namespace and ./guidelines.sh on the serve namespace; ./promote.sh copies from one to the other. All of them read the names from this config.

Before committing changes to `schema/models.yaml` or `clients/python/shopkit_client.py`, add an entry
under `## Unreleased` in `CHANGES.md` and bump `clients/python/VERSION` (minor version for a new field).

In the shopkit repository, follow the full four-step pipeline when adding a field to a model: (1) edit
`schema/models.yaml`, (2) run `make generate`, (3) run `make migration NAME=<name>`, (4) run `make test`.

When adding an optional field to a model in shopkit, declare it with `{type: str}` …

Show the evidence

Cortex records what the evolve plugin did on every request. Two ways to show that Codex's guidelines came from Cortex:

In the terminal

./injected.sh codex          # latest Codex session; ./injected.sh claude for Claude Code's

It prints three things for the session's first request, the one the plugin injects into:

  1. plugins.evolve, the plugin's record: "injected": true, the guideline ids, and sources, the session each guideline was learned from. In Flow 1 that's Claude Code's session.
  2. The invocation: modify · body_rewritten when the block was added. Claude Code's source session shows skip · no_guidelines, since nothing was served yet.
  3. The block itself, taken from the body Cortex forwarded to the model: the <evolve-guidelines> block at the start of the first user message.

In agentop

agentop observe -endpoint "http://127.0.0.1:${CORTEX_API:-47701}"

Open the Codex session, then its first request's detail:

  • The request's title line ends in modify evolve: the plugin changed what was sent.
  • Under plugins › evolve: the same record, injected, ids and sources.
  • Under raw: forwarded: rewritten by a plugin: … → …, and forwardedBody, the exact body the model received, with the block in the first user message. The parsed messages show what Codex sent, before the plugin added it.
  • Every later request in the session is injected too. Within the plugin's cache window (cache_ttl_seconds, 60 s on the rehearsal setup) they reuse the fetched set and show "cached": true; after it, the plugin refetches the same guidelines.

For what was learned and what is served: ./candidates.sh list and ./guidelines.sh list, or everything with its metadata: ./entities.sh | jless.

Troubleshooting

  • No candidates. The dev Cortex log should show evolve: sent idle session to learn from about 30 s after the session's last request. If it shows sending session to learn from failed, check the Evolve server's log for the model error. A config change, including ./inject.sh or ./prepare.sh, drops a session that hasn't been sent yet, so don't switch anything between 1.2 and 1.3.
  • Guidelines not injected. ./inject.sh status should say ON and ./guidelines.sh list should list them. Guidelines are fetched once per session, so start a new Codex session after loading.
  • No hook rejections at all. The hooks run Python from the shopkit virtualenv. Check $WALK/codex-user/.zprofile puts it on PATH, and that ./reset.sh set core.hooksPath.
  • Interactive Codex answers but no session appears in the dev Cortex. Its background process started before codex-home/.env pointed at the dev Cortex: restart it (command).
  • Claude Code exits straight away. The trust dialog's default is "No, exit"; choose "Yes, I trust this folder".
  • Codex runs but Cortex shows a pending:codex@… bucket instead of a session: add Session-Id to session.id_headers and restart the dev Cortex.

Script reference

In demos/cortex-repo/live/. Source env.sh first. Paths can be overridden with EVOLVE_ENV_FILE, CORTEX_CONFIG, CODEX_HOME_DIR, CODEX_USER_HOME and DEMO_ROOT.

ScriptDoes
check.shChecks the running setup: Evolve, the dev Cortex and its evolve plugin, Claude Code's and Codex's routing, the virtualenv. Says how to fix whatever isn't ready.
prepare.sh [idle]Sets the evolve plugin to inject and learn with a short idle wait (default 30 s), and empties cortex and cortex-candidates.
reset.sh [claude|codex]A fresh shopkit with one commit and its hooks enabled, at $WALK/live/claude-shopkit and/or $WALK/live/codex-shopkit (both without an argument).
commits.sh [claude|codex]Each demo repository's commits, and the files the last one changed.
injected.sh [codex|claude] [session]For the agent's latest session, or the one given: the evolve plugin's record, its invocation, and the guidelines block in the forwarded body.
claude.sh / codex.shStart the agent in its demo repository through the dev Cortex. Extra arguments are passed on (for example exec "…").
candidates.sh list | show <id> | wait [s] | wait-and-promote [s] | clearWhat Evolve learned. wait polls until new candidates appear; wait-and-promote then promotes all of them, skipping the review step.
promote.sh <id>…Copies candidates into the served namespace with their metadata (evolve entities export → import --append).
guidelines.sh list | clear | load [file]What the dev Cortex serves; load replaces it from a file (default guidelines/rules-20261111.json).
entities.sh [served|learned|<namespace>]Every entity, with all its metadata, as JSON on stdout; both namespaces by default. For browsing: ./entities.sh | jless.
inject.sh on | off | statusSwitches injection in the dev Cortex through its config hot-reload.
