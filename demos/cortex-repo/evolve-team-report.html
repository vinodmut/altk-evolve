Evolve inside Cortex: what we built, what we measured, what we need from Evolve

Cortex is a proxy that sits in front of coding agents. We added a Cortex plugin that records each session, sends it to a stock Evolve MCP server to learn from, and injects reviewed guidelines into later sessions. Nobody grades or labels anything. This report covers the architecture, a fresh end-to-end run (learned from Claude Code, applied to new Claude Code and Codex sessions), a follow-up that changed only Evolve's guideline prompt, the design decisions, and the questions that are Evolve's to answer.

Summary

  • The loop works end to end with a stock Evolve server. Cortex records a session, sends it to process_trajectory once idle, a person promotes candidates from cortex-candidates to cortex, and get_guidelines_with_attribution serves them to the next session. No Evolve API changes were needed.
  • Learning from one Claude Code session helped both a new Claude Code session and a Codex session (a different vendor's agent on a different model). Each guided session committed after at most one rejection. Codex baselines needed up to two.
  • With the default prompt, a rule the session ran into was learned only as recovery advice. Evolve learned "bump VERSION" as a concrete step, and every guided run got it right. It learned "add a CHANGES.md entry" only as "read the hook's error message", and both guided Claude Code sessions still hit that rejection.
  • A prompt that states rules fixed it (follow-up, Nov 11). A new opt-in rules prompt states each requirement an error message spells out as a step to take first. On the same trajectory it produced the rule where the default produced recovery advice. In a fresh run, guided sessions committed first time 3/4 (0/4 before), no guided session missed the changelog, and Claude Code's cost per task halved.
  • The open question for Evolve is scope. These guidelines name one repository's files. Nothing yet stops them being served in another repository.

1

Architecture

Evolve never calls Cortex. ① runs on the request path once per session, bounded by timeout_ms, and fails open: if Evolve is down, requests go through unchanged. ② runs from a background ticker after the response has been sent, so it never delays a request.

Why a proxy

Cortex already sees every agent's model calls and tool results, for every coding agent. So one integration covers Claude Code, Codex, Bob and opencode, with no change to any of them.

Why two namespaces

Learned guidelines land in cortex-candidates, which is never served. Only what a person copies to cortex is injected. Text from a tool result, such as a web page an agent fetched, can't become a standing instruction without review.

Code: Cortex plugin core/plugins/evolve on vinodmut/cortex@evolve-plugin; Evolve on vinodmut/altk-evolve@rossocortex.

The block is the same bytes on every turn, so the provider's prompt cache keeps hitting. The plugin strips this block (and other reminders) from trajectories it sends back, so Evolve doesn't learn its own guidelines.

3

The experiment

Nov 10, 2026

Question: after learning from one Claude Code session, do fresh sessions of Claude Code and of Codex do a different task in the same repository better?

The repository

shopkit, a small sample repository whose git hooks enforce rules no prompt mentions. A commit that changes the schema or the Python client is rejected unless:

  • CHANGES.md has an entry under ## Unreleased;
  • clients/python/VERSION is bumped (minor for a new field);
  • the subject is a lower-case Conventional Commit, for example feat(users): add nickname.

The hooks print exactly which rule failed, so a session's rejections are in its tool results.

Procedure

  1. Fresh state. A new Evolve data directory with empty cortex and cortex-candidates namespaces. Nothing from earlier runs.
  2. Training (injection off). Claude Code adds an optional nickname field to users and commits. Cortex sends the session to Evolve after 90 s idle.
  3. Review. All four candidates were promoted unchanged (judged below).
  4. Evaluation. A different task, adding an optional discount_code field to orders, in a fresh clone each time. Four pairs, interleaved: guided (injection on) then baseline (injection off), for Claude Code then Codex, twice.

What Evolve learned

The training session made 39 tool calls: 18 by the main agent over 15 turns, the rest by a subagent Claude Code started. Cortex sent the main agent's 34 messages to Evolve. It was rejected once:

6

What the results say

A concrete guideline removes its mistake, for both agents

Every baseline missed the VERSION bump. No guided session did. Both Claude Code and Codex read guideline 4 and bumped clients/python/VERSION before their first commit. This holds across vendors: the guideline was learned from Claude Code (Sonnet 4.6) and applied by Codex (gpt-5.6-luna).

A recovery guideline doesn't prevent its mistake

Guideline 3 says to read hook failures carefully. It says nothing about CHANGES.md. Both guided Claude Code sessions still committed without a CHANGES.md entry, were rejected, and then fixed it. No session in any arm read .githooks/ before committing, which is what "read the hooks" would have led to.

The guided Codex sessions did add a CHANGES.md entry before their first commit. Codex reads more of the repository up front, and with the guidelines in mind it updated both release files together. That's the agent's behaviour, not a guideline Evolve learned.

What was never in the training session wasn't learned

Training never broke the commit-subject rule, so Evolve had nothing to learn there. Both guided Codex sessions were rejected for it. A rule that one agent satisfies by habit (Claude Code writes lower-case Conventional Commit subjects) can still trip another agent, so learning from one harness leaves gaps for others.

Cost and tool calls

For Codex, guided sessions used fewer tool calls (9 and 12 against 13 and 15) and 23% fewer input tokens, because they avoided a rejection round trip. For Claude Code, calls and tokens were flat. Both arms had exactly one rejection, so there was no round trip to save.

!

Takeaway for Evolve: the gain came from the one guideline that stated a repository-specific fact as a step. Cortex sessions have no outcome, so they get the prompt's no-evaluation branch. That branch asks for guidelines specific to the trajectory, but nothing in it asks for a requirement an error states to be written as a step to take beforehand. The follow-up tests exactly that change.

Follow-up: a prompt that states rules

Nov 11, 2026

One change to Evolve, and one to the experiment. The standard generator's prompt is now a setting, guidelines_prompt (EVOLVE_GUIDELINES_PROMPT, or per processing profile). default is the existing prompt and stays the default (1b84e3dc). The new rules prompt is the default plus one section:

# Requirements the environment stated
When a tool result, a check, a hook or an error message states a requirement (a file to update, a command to run, a format to follow), write a guideline that states that requirement as a step to take *before* the action it blocked. Name the files, sections, commands and formats exactly as the evidence states them. …
- Cover each stated requirement. …
- Put the condition that triggers the requirement (for example, which files changed) in the trigger.
- Advice about recovering from an error is for errors whose message states no requirement.

Its example is from an unrelated domain (a deploy script), so it can't hand the learner this repository's rules. Retrieval is unchanged: embedding similarity of the task, with no scope.

Same trajectory, two prompts

Today's training trajectory (46 messages, rejected once for the changelog and version) learned twice with each prompt, in a separate store:

PromptWhat it learned about the rejection
default"Run all pre-merge checks (make check) before committing to discover hook requirements…" and "When a pre-commit hook rejects a commit…, address each message exactly as stated before retrying." No guideline names CHANGES.md.
rules"Before committing in this repository, update CHANGES.md by adding an entry under the ## Unreleased section…, and bump clients/python/VERSION to the next minor version when a new field is added to the Python client." Trigger: "When schema/models.yaml is modified…"

The rules prompt also learned the workflow as one step list (make generate, make migration, make check && make test): 2 guidelines in place of 4. The two runs per prompt were word for word identical, which may be the proxy caching identical requests, so they show the result is stable here, not that it was sampled twice.

Questions for the Evolve team

Each is a design choice that changes what the integration can do. Evolve marks ones that are Evolve's to decide; both marks ones to decide together.

Evolve1. Should guidelines be allowed to be specific to a scope, such as a repository?

The guidelines that worked name one repository's files and rules. Evolve stores no scope with a guideline, and retrieval ranks by task similarity, so a "add a field" task in another repository would be served them too. (The prompt's outcome branch also asks to leave out values specific to the task; Cortex sessions don't use that branch.)

Cortex knows each session's working directory and could send it as a scope. That would need Evolve to (a) let a guideline name concrete files and rules when they belong to its scope, (b) store the scope, and (c) filter or weight retrieval by it. Without scope, a repository-specific fact learned in one repository would be served in every other.

Evolve2. Should a guideline state the rule, or how to recover?

Evolve turned the hook's CHANGES.md message into "read hook failure messages carefully", and every guided Claude Code session was still rejected for it.

When an error message spells out the rule ("changed without an entry in CHANGES.md under '## Unreleased'"), the useful guideline is the rule itself, stated as a step before the action. Tried on Nov 11 as the opt-in rules prompt (follow-up): it did exactly this, and guided runs then committed first time. Should it become the default, for every client of Evolve or for coding sessions only?

Evolve3. What should the default trajectory window be for long coding sessions?

The default keeps 50 steps: the first 40 and the last 10. In an earlier run this dropped the step with the most useful rejection. The demos raise it to 150 through the plugin's processing profile.

Options: a larger default for agentic sessions; always keeping failed steps and the step after each; or letting the caller mark steps that must be kept.

both4. Who owns the review gate, and could it become automatic?

Today a person copies candidates between two namespaces with the Evolve client. Evolve doesn't know which namespace is "reviewed".

Options: Evolve owns review states (as c52867c2 once did) so every client of Evolve gets the same gate; or Cortex holds guidelines back from some sessions and promotes only those that measurably help. Cortex can measure, since it records which guidelines each session got and how it went. Evolve would need to accept the outcome per guideline.

Evolve5. How should retrieval work for a coding agent's first message?

The plugin sends the first user message as task. Claude Code's first message carries several kilobytes of environment context before the real request, which Cortex strips only if it's in a <system-reminder>.

Retrieval similarity is source_task by default. Is the first message the right key? Would Evolve rather receive a short task summary, the working directory, or the tool list?

both6. Should guidelines be retrieved again when the task changes?

Once per session, then cached. A session that moves to a new task keeps its first set.

Finer options cost prompt-cache hits or need a trigger: on each new user instruction, or just in time after a tool error that matches a guideline's trigger. Evolve already stores a trigger per guideline; using it at retrieval time is unexplored.

Evolve7. Should learning be told which agent and model produced a session?

The plugin sends agent_id and session_id as metadata. The agent ID is stored on each candidate; the model isn't used.

Two uses: retrieval could avoid serving one agent's tool-specific advice (for example "use the Read tool") to another agent, and learning could note what one agent does by habit that another doesn't (the commit-subject gap here). get_entity also refuses guidelines owned by another agent_id, which is why the plugin reads them with list_entities. Is that ownership check intended for cross-agent serving?

both8. Where should redaction happen?

Session content, including tool output, goes to Evolve and its learner LLM unredacted. Evolve's hooks have a secrets plugin; the Cortex path doesn't use it.

Redacting in Cortex covers every agent at one point. Redacting in Evolve covers every client of Evolve. Either way, it's a prerequisite for sharing guidelines between people.

Evolve9. Should Evolve learn from what an environment rejected, as a first-class signal?

Lessons come from tool results, read by the learner.

Cortex sees structured failures it could label: a hook rejection, a policy denial from one of its guardrail plugins, a command's non-zero exit. A typed "this action was rejected because X" signal could make learning both cheaper and more precise than reading free text.

Future work

For Evolve

  1. Decide whether rules becomes the default prompt (question 2), after trying it on other kinds of trajectory (AppWorld, τ²-bench), where the default prompt's results were measured.
  2. Scope (question 1): store where a guideline applies and filter retrieval by it, before rule-stating guidelines are shared across repositories.
  3. Upstream the three learning fixes (91143f06, 95c177f6, 3aab085f).
  4. A larger or failure-aware trajectory window by default (question 3).
  5. Per-guideline outcome input, so a caller can report "sessions with this guideline did better or worse" (question 4).

For Cortex

  1. Holdout measurement: hold guidelines back from a share of sessions and report rejected commits, tool calls and cost with and without each guideline.
  2. Keep unsent turns across a config reload. In this run, a reload (which the experiment used to switch injection) dropped the evaluation sessions' pending turns, so they were never sent to Evolve. Harmless here, but in normal use any config change loses learning.
  3. Send the working directory as a scope once Evolve accepts one.

For the experiments

  1. More pairs, across several held-out tasks, to put error bars on these effects.
  2. A Codex-trained arm (learn from Codex, apply to Claude Code). Cortex now records Codex's tool results, which it didn't until this week (rossoctl/cortex#1771).
  3. A real repository with real conventions, with consenting developers.
